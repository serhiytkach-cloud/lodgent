# 0013. AWS infrastructure (CDK)

Date: 2026-10-11 · Status: accepted

## Context
Lodgent runs as three containers (api, worker, web) plus a one-off migration task, against PostgreSQL with pgvector, a job queue with recurring schedules, KMS envelope encryption of integration tokens, SES email and Cognito sign-in (ADR 0005). The infrastructure has to be reproducible per environment (dev, prod), safe by default, and synthesizable in CI with no AWS credentials. Deployment itself (images, pipeline, migrations) is ADR 0012.

API checks (October 2026) against the installed `aws-cdk-lib` 2.273.0 typings: stable L2 constructs exist for EventBridge Scheduler (`aws-scheduler`, `aws-scheduler-targets.SqsSendMessage`), Cognito feature plans (`FeaturePlan`, `StandardThreatProtectionMode`, `ManagedLoginVersion`), the native IAM OIDC provider (`OidcProviderNative`), ECS `containerInsightsV2`, RDS `databaseInsightsMode`, and the post-quantum ALB policy `ELBSecurityPolicy-TLS13-1-2-PQ-2025-09`. `ApplicationLoadBalancer.logAccessLogs` needs a concrete region, which is one reason the region comes from context. WAF, the WAF logging configuration and the ADOT collector use L1/plain configuration.

## Decision

**Synthesis.** `infra/bin/app.ts` defines every stack from CDK context with defaults that synthesize offline (`pnpm cdk:synth`). There are no lookups. The account is environment-agnostic (taken from the deploying credentials) and the region comes from context (`region`, per environment `<env>.region`, default `eu-central-1`). Context is validated with Zod (`infra/lib/config.ts`), and features that need operator input are off until it is given. The recommended CDK feature flags are set in `cdk.json`, except that cross-stack references stay `strong` (CloudFormation exports). `-c env=dev` synthesizes a single environment, which the pipeline uses.

**Stacks per environment**, in deploy order (`<slug>-<env>-…`):

| Stack | Contents |
| --- | --- |
| `network` | VPC in 2 AZs: public, private app (NAT egress) and isolated data subnets. NAT gateways: 1 in dev, 2 in prod. S3 gateway endpoint. In prod, interface endpoints for ECR (api, dkr), CloudWatch Logs, Secrets Manager, SQS and KMS. VPC flow logs to CloudWatch (REJECT in dev, ALL in prod). The default security group is restricted. All security groups and their rules live here, so other stacks never reference each other in a cycle. |
| `data` | KMS keys `data` (RDS storage, Performance Insights, secrets) and `app` (token encryption, `KMS_KEY_ID`), both with rotation. RDS PostgreSQL 16. App secret `<slug>/<env>/app`. Jobs queue and its DLQ. The three ECR repositories. Cognito user pool and web client. SES identity and configuration set. |
| `platform` | ECS cluster (Container Insights, Fargate and Fargate Spot) with a private Cloud Map namespace. Log groups. ALB, WAF, certificate and DNS. The `migrate` task definition. EventBridge schedules. SNS alarm topic. Alarms for the load balancer, database and queue. |
| `services` | api, worker and web task definitions and services, autoscaling, per-service alarms, dashboard. |

`<slug>-github-deploy` (OIDC provider and deploy roles) is deployed once per account by an administrator.

The split follows lifecycle. `data` exists before the first image push (registries) and before the first services deploy (the operator fills the app secret). Everything the migration needs exists before the services roll, so the pipeline can migrate first.

**Database.** RDS for PostgreSQL 16, which ships pgvector; migration 0000 runs `CREATE EXTENSION vector` as the master user.
- Placement: isolated subnets, not publicly accessible. The database security group admits only the api, worker and one-off task groups.
- Encryption: storage with the `data` key, CA `rds-ca-rsa2048-g1`, and a parameter group with `rds.force_ssl=1`, slow-statement logging and a 5-minute idle-in-transaction timeout.
- Storage and monitoring: gp3 with storage autoscaling, Performance Insights (free 7-day tier), log exports to stack-owned log groups.
- Credentials: generated by Secrets Manager (`<slug>/<env>/database`). Tasks receive `DATABASE_USER`/`DATABASE_PASSWORD` as ECS secrets and the host, port and name as plain environment. `loadConfig()` builds the URL, percent-encoding the parts and adding `sslmode=verify-full`.

| | dev | prod |
| --- | --- | --- |
| Instance | `db.t4g.micro`, single-AZ | `db.t4g.medium`, Multi-AZ |
| Backups | 3 days | 30 days |
| Deletion | snapshot | deletion protection, retained |
| Enhanced Monitoring | off | 60 s |

**Jobs.** An SQS standard queue with SQS-managed SSE (free, and messages hold job types and ids, no PII) and TLS-only access.
- Visibility timeout 15 minutes, which covers the longest job. Long polling 20 s.
- After 5 receives a message moves to the DLQ (14 days retention).
- `SCHEDULES` moved to `@lodgent/shared` (pure data); `@lodgent/application` re-exports it and keeps `LocalScheduler`.
- Each entry becomes an EventBridge Scheduler schedule in group `<slug>-<env>`, UTC. It sends `{ type, payload, dedupeKey }` to the jobs queue, the format `SqsJobQueue` sends and `SqsJobConsumer` parses.
- Maximum event age is one interval. Undeliverable runs go to the same DLQ.
- The scheduler role trusts `scheduler.amazonaws.com` only for this account's schedule group.

**Edge.** An internet-facing ALB (dropping invalid headers, access logs to an SSE-S3 bucket, since ALB logs cannot use SSE-KMS) with two IP target groups health-checked on `/healthz`.
- With `domainName`: HTTPS (post-quantum TLS 1.2+/1.3 policy), HTTP 301 to HTTPS, and host routing (`api.<domain>` → api, `app.<domain>` → web, anything else 404).
  - The certificate is either imported (`certificateArn`) or requested with DNS validation: automatic with `hostedZoneId`, otherwise pending until the operator adds the CNAMEs.
  - With a hosted zone, Route 53 aliases are created.
- Without a domain: plain HTTP on the ALB name. `/v1/*`, `/mcp`, `/webhooks/*`, `/openapi*.json` and `/readyz` go to the api, everything else to the web. This is a smoke-test mode: Cognito accepts HTTP callbacks only for localhost, so dashboard sign-in needs a domain.
- The web server reaches the API through Cloud Map (`http://api.<slug>-<env>.internal:4000`), not through the ALB. Server-side traffic therefore never meets the WAF rate limit from a single NAT IP.

**WAF.** A regional web ACL on the ALB, in order:
1. Amazon IP reputation list.
2. A per-IP rate limit (2000 per 5 minutes; `/webhooks/` exempt because Stripe and Apaleo retry in bursts from few IPs).
3. Core rule set.
4. Known bad inputs.
5. SQLi.

Two core-rule-set rules are switched to count and re-enforced by our own label rules with narrow exceptions:
- `SizeRestrictions_BODY` (bodies over 8 KB, the most an ALB-attached WAF inspects) is blocked except on `/webhooks/` (Stripe events are often larger; payloads are signature or token verified), exactly `/mcp` (JSON-RPC tool calls) and `/app/` (signed-in dashboard; Next.js server actions post whole forms).
- `NoUserAgent_HEADER` is blocked except on `/webhooks/`.

Every other rule still inspects those paths. The anonymous-IP and hosting-provider lists and Bot Control are deliberately not used, because AI agents call from cloud IP ranges. Only blocked and counted requests are logged, to `aws-waf-logs-<prefix>`, with `authorization`, `cookie` and `x-api-key` redacted.

**Services.**
- Fargate in private subnets without public IPs. Dev uses Fargate Spot.
- Images are `<slug>-<env>-{api,worker,web}:<imageTag>`. The repositories have immutable tags, scan on push and lifecycle rules.
- Each service gets the contract environment plus the production Apaleo endpoints. Secrets come only as ECS secrets: api and worker get every app-secret key except `COGNITO_CLIENT_SECRET`, which only the web gets. Execution roles may decrypt the `data` key only via Secrets Manager.
- api, worker and migrate run with a read-only root filesystem and a writable `/tmp` volume. The web keeps a writable filesystem for the Next.js cache. No container is privileged. tini in the images is PID 1.
- Deployments use the circuit breaker with rollback at 100/200 %. The health-check grace period is 60 s. The worker gets 120 s to finish a job on stop.
- Autoscaling: api and web on CPU (60 %) and ALB requests per target. The worker scales on queue depth both ways and on CPU for scale-out only, so the two policies cannot flap.
- api and worker run an AWS Distro for OpenTelemetry collector sidecar (`aws-otel-collector:v0.50.0`, non-essential, started first). It is configured inline: OTLP/HTTP on `127.0.0.1:4318`, ECS resource detection, export to X-Ray. The task roles get the X-Ray write actions.

**Least privilege.**
- api task role: `GenerateDataKey`/`Decrypt` on the `app` key, and send to the jobs queue.
- worker task role: the same, plus consume jobs and `ses:SendEmail`/`SendRawEmail` on identities and the configuration set of this account and region (the SES sandbox also authorizes the recipient identity).
- web task role: no data access.
- migrate: named execution and task roles (`<prefix>-migrate-execution`, `<prefix>-migrate-task`) that read only the database secret.

**Auth.** A Cognito user pool on the Essentials plan.
- Sign-in by email, self sign-up, verified email, optional TOTP MFA (no SMS), 12-character passwords, email-only recovery. Deletion protection and retention in prod.
- Web client: authorization-code flow only, with a client secret and PKCE (the web app sends both), scopes `openid email profile`, token revocation, and user-existence errors suppressed. Callbacks are `https://<web>/auth/callback` (dev also allows `http://localhost:3000`).
- Hosted UI domain prefix `<slug>-<env>-<account id>`, unique per account.
- Threat protection (formerly advanced security) needs the Plus plan, billed per MAU, so it is opt-in with `cognitoThreatProtection=audit|enforced`.
- Cognito sends its own emails with the default sender (low daily limit). Switching it to SES is a later configuration change.

**Email.** With a domain: an SES domain identity with Easy DKIM, a custom MAIL FROM `mail.<domain>`, and a configuration set (TLS required, reputation metrics, account suppression for bounces and complaints) as the identity's default. The records go into the hosted zone, which may be a parent zone. Without a hosted zone, the DKIM CNAMEs are stack outputs.

**Observability.**
- SNS topic `<prefix>-alarms`, with an email subscription from context.
- Alarms, all with OK notifications:
  - ALB 5xx rate above 5 % (with at least 20 requests).
  - p95 target response time per service (api 2 s, web 3 s).
  - Unhealthy targets.
  - Database CPU, free storage below 10 %, and connections above 80 % of the estimated `max_connections`.
  - DLQ not empty; oldest job older than 30 minutes.
  - Per service: CPU, memory, and no running task.
- One CloudWatch dashboard per environment.

**GitHub deploy access.** `token.actions.githubusercontent.com` OIDC provider (or `githubOidcProviderArn`), and per environment a role `<slug>-<env>-github-deploy`.
- Trust: `StringEquals` on `aud = sts.amazonaws.com` and `sub = repo:<githubRepo>:environment:<env>` (no wildcards).
- Permissions:
  - assume the CDK bootstrap roles `cdk-<qualifier>-*`;
  - ECR login and push to the three repositories;
  - describe, register and deregister task definitions;
  - `ecs:RunTask` on the migrate family in this cluster only, and `iam:PassRole` for the two migrate roles to ECS only;
  - describe and stop tasks; describe services;
  - read the migrate logs, the environment's stack outputs and the exports.
- `githubDeployEnvs` limits which roles exist in an account, so a dev workflow never gets a role in a separate prod account.

**Outputs.** Exports named `<slug>-<env>-<Name>`, read by the pipeline with `aws cloudformation list-exports`: `AppSubnetIds`, `AppSecurityGroupId`, `{Api,Worker,Web}RepositoryUri`, `AppSecretArn`, `DatabaseEndpoint`, `DatabaseSecretArn`, `JobsQueueUrl`, `UserPoolId`, `UserPoolClientId`, `CognitoDomain`, `AppKmsKeyArn`, `ClusterName`, `MigrateTaskDefinitionArn`, `MigrateTaskFamily`, `MigrateLogGroupName`, `LoadBalancerDnsName`, `WebUrl`, `ApiUrl`, `AlarmTopicArn`, `{Api,Worker,Web}ServiceName`, `GithubDeployRoleArn`.

**Tags and removal.** Stack tags `app=<slug>` and `env=<env>` (propagated by CloudFormation). With `protectData` (prod default):
- RETAIN on keys, secrets, the database, the user pool, registries, log groups and the access-log bucket;
- deletion protection on the database, user pool and ALB;
- termination protection on the stacks.

Dev cleans up after itself, except for a final database snapshot.

**Tests.** `infra/test` (vitest + `aws-cdk-lib/assertions`) checks:
- the database: encryption, privacy, force_ssl, Multi-AZ and protection in prod, and that only the app groups may reach it (never `0.0.0.0/0`);
- the jobs queue: DLQ and encryption;
- the WAF association and rule scoping;
- the ECS tasks: non-privileged, and secrets only through Secrets Manager;
- the per-role permissions;
- that there is one schedule per `SCHEDULES` entry, targeting the jobs queue with a message the consumer schema accepts;
- that the OIDC trust is limited to the repository and environment;
- the routing modes, exports and context validation.

## Rejected alternatives
- **Aurora Serverless v2:** a higher floor price than a small instance for steady low load. RDS PostgreSQL is enough, and Aurora remains a later migration path.
- **RDS Proxy:** extra cost. At this scale pools are small (10 per process).
- **ECS Service Connect:** adds an Envoy sidecar to every task. Cloud Map DNS is enough for one internal call path.
- **SSE-KMS on SQS:** cost and IAM coupling for no PII.
- **CloudFront in front of the ALB:** not needed yet; it can be added with the WAF moved to CLOUDFRONT scope.
- **Lookups (`fromLookup`):** they require credentials at synth time.
- **One app stack:** it could not migrate between the platform and service changes, and the first deploy would need images and secrets before the registries and secret exist.

## Operator input
- **Domain:** `domainName` plus `hostedZoneId` (or `certificateArn`, or adding the ACM validation CNAMEs by hand). Dashboard sign-in needs it.
- **Alarm email:** `alarmEmail`; confirm the SNS subscription.
- **App secret:** fill `<slug>/<env>/app` before the first services deploy. `SIGNING_SECRET` is generated. `INTERNAL_API_TOKEN` and `AUTH_DEV_SECRET` need random values (min 8 and 32 characters). `COGNITO_CLIENT_SECRET` comes from the web client.
- **SES:** request production access (leave the sandbox), and publish DMARC for the domain.
- **Bootstrap and GitHub:** `cdk bootstrap`, ideally with a narrower `--cloudformation-execution-policies` than AdministratorAccess. Deploy `<slug>-github-deploy` once per account, and set the GitHub environments (`dev`, `prod` with reviewers) with the role ARN.
- **Webhooks:** register the Stripe and Apaleo webhook URLs on the API host.

## Consequences
- The app connects as the RDS master user. A dedicated least-privilege login role, with RDS-managed rotation that restarts the tasks, is a follow-up: it needs a migration and a second secret. Secrets are not rotated automatically, because running tasks keep the values they started with.
- Adding a scheduled job is a data change in `packages/shared/src/schedules.ts`. Adding an app secret key means changing `APP_SECRET_KEYS` and adding the key to the existing secret before deploying, or tasks fail to start.
- WAF false positives are tuned by switching a single managed rule to count and re-enforcing it with a scoped label rule, as done for body size.
- Changing the domain, the Cognito domain prefix or the database instance identifier replaces resources. The instance identifier is fixed, so a replacement fails loudly instead of silently creating a new database.
